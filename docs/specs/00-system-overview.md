## 1. 背景・目的

- 既存のハードウェア（ATEM Mini）と自作ハードウェア（自作スイッチングモジュール群 + Pico 2W）、およびネットワーク技術（SRT / NDI / WebAPI）を融合した、次世代のハイブリッドIP映像スイッチャーシステムを構築する。
- PC上に常駐する制御アプリを「脳」とし、複数プロトコル（UVC / NDI / SRT）の映像入力・PiP合成・仮想カメラ出力・タリー送出・外部機材（ATEM）の遠隔制御を一元化する。
- DIYでありながらプロ用スイッチャーに匹敵する多人数オペレーション（メイン/サブ分業）と拡張性を実現する。

## 2. システムアーキテクチャ

```text
[ サブ ATEM Mini ] ──(SRT/HDMI/NDI)──→ [ メインPC (常駐App) ] ──(仮想WebCam/HDMI)──→ [ 配信/録画/OBS等 ]
        ▲                                    ▲        │
        │ (ATEM遠隔制御: UDP 9910)            │        │ (UDPタリー: 9999 ブロードキャスト)
        └────────────────────────────────────┘        ▼
                                             ▲   [ ワイヤレスタリー子機(ESP32) ]  [ 赤/緑 LED ]
                                             │ (WebSocket / WebAPI: 8080)
                                    (USB/HID/Serial)
[ 自作コントローラー: Pico 2W ] ──┬── (USB直結) ──→ メインPC
        │                         └── (USB-OTG) ──→ [ スマホ (Web App) ] ──(Wi-Fi/WebSocket)──→ メインPC
        │
        ├─(内部制御: 後日詳細化)──→ [ 各スイッチングモジュール内マイコン ]
        └─(HDMI DDC/I2Cスニッフィング)──→ [ 物理タリー抽出 ]
```

### 2.1 ハードウェア構成方針（確定事項 / 2026-07-17）

- 各スイッチングモジュールは内部にマイコンを搭載する。
- それらを **Pico 2W (RP2350 + Wi-Fi)** が統括制御する。
- **外部（PC・ネットワーク）と実際に通信するのは Pico 2W のみ**。個々のモジュール内マイコンは Pico 2W とのローカル内部通信のみを行う。
- Pico 2W ↔ モジュール内マイコン間の内部制御プロトコル（I2C/UART/SPI 等の選定含む）は**別途詳細化する（TBD）**。
- リポジトリ内の既存 KiCad 設計（`softswitcher_rp2040_v2` / `softswitcher_module_sw4` / `softswitcher_hdmi_v1` 等）は参考資産とし、本方針に合わせてハードウェアは再検討段階にある。

## 4. 共通プロトコル定義

各コンポーネントはこの共通定義に準拠する。詳細な各エンドポイントは個別仕様書に記載。

### 4.1 コントローラー入力イベント (WebSocket, JSON)

```json
{
  "event": "button_press",
  "data": {
    "controller_id": "main",
    "button_id": 3,
    "timestamp": 1773663861000
  }
}
```

- `controller_id`: コントローラー識別子（例: `main` / `sub`）。Pico 2W の Unique ID もしくは設定で紐付ける。

### 4.2 スイッチャー設定変更 API (POST `/api/v1/config`)

```json
{
  "target_channel": 2,
  "source_type": "SRT",
  "source_url": "srt://192.168.1.100:9000?mode=caller",
  "pip_settings": {
    "enabled": true,
    "x_position": 1420,
    "y_position": 80,
    "width": 480,
    "height": 270,
    "opacity": 1.0
  }
}
```

### 4.3 独自タリー配信プロトコル (UDPブロードキャスト) 【確定】

- 送信元: メインPC常駐アプリ
- 宛先: `255.255.255.255:9999`（LANブロードキャスト）
- 送出契機: 状態変化時に即時、加えて定期（例: 4回/秒程度）で冗長送信
- ペイロード（軽量JSON、将来バイナリ化も可）:

```json
{
  "active_pgm": [1, 5],
  "active_pvw": [2]
}
```

- NDI経由・HDMI DDC抽出は補助経路として検討可能だが、**主経路は本UDPブロードキャストで確定**。

### 4.4 ポート一覧（共通）

| ポート | プロトコル | 用途 |
| --- | --- | --- |
| 8080 | HTTP/WebSocket | 設定WebAPI・コントローラー入力受信 |
| 9000 | SRT (Listener) | 映像入力（ATEM PGM等） |
| 9999 | UDP broadcast | タリー配信 |
| 9910 | UDP | ATEM遠隔制御（ATEM純正プロトコル） |

## 5. 非機能要件（システム共通）

- **低遅延**: 映像パスはゼロ〜低バッファ。SRTはLAN前提で `latency` を最小化（20〜50ms目安）。
- **コントローラー→切替反映**: 5ms以下を目標（WebSocket経路）。
- **同時操作安全性**: メイン/サブ2名同時操作でも取りこぼし・競合が起きないよう、キー入力はイベントキューで直列化。
- **拡張性**: 入力ソース10ch以上に対応。子機・コントローラーは複数台接続可能。
